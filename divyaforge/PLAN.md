# DivyaForge — M0 Prototype Plan

**Scope:** One deity (Ganesh) end-to-end, per `prd-divyaforge-v1.1.md` §12 (M0) and the
kickoff prompt. This document is the pre-coding plan: architecture, data model, file
structure, and task checklist.

### Key architectural decisions (details in DECISIONS.md)

1. **Designs are JSON parameter configs, never meshes** (PRD §9). A design is a
   `DesignConfig` object with a `schemaVersion`. Share links `/d/[configId]` load the
   exact config read-only with a “Customize this” fork button.
2. **Zero-code-change part swapping.** The renderer never special-cases a part. Every
   catalog part is a **GLB file loaded from `meshUrl`** and attached to a named socket
   (slot → socket mapping is data). Placeholder GLBs are generated by a build script
   from primitives; replacing them with artist GLBs = replacing files + catalog rows.
   The *body* is a procedural parametric humanoid with an elephant-head placeholder
   (explicitly allowed by the kickoff), exposing named bones/sockets + morph params.
3. **Storage adapter with demo mode.** All persistence flows through one adapter
   interface. With Supabase env vars → real auth/Postgres. Without → localStorage +
   config-encoded share links, so the repo runs out-of-the-box (`npm i && npm run dev`).
4. **Constraint engine is enforced twice**: in the UI (denied parts render disabled with
   the rule’s reason; equip is impossible) and server-side in `/api/designs` +
   `/api/orders` before any insert. “Divine Inspiration” samples only from
   `canEquip`-allowed parts.
5. **Pricing is a pure function** used identically by the live Buy tab and the orders
   API (server recomputes; client price is display-only).

## 2. Data model

### 2.1 DesignConfig (the saved/shared artifact, schemaVersion = 1)

```ts
{
  schemaVersion: 1,
  deityId: "ganesh",
  form: "standing" | "seated",          // deity form presets
  face:  { eyeOpen, browTilt, smile, trunkCurl, earSize, tuskLength },  // 0..1 sliders
  body:  { height, weight, armCount: 2 | 4 },
  pose:  "ashirwad" | "dhyana" | "nritya",
  parts: { [slotId]: partId | null },   // slots: vastraLower, vastraUpper,
                                        // handR1, handL1, handR2, handL2, base
  colors:  { [zoneId]: "#rrggbb" },     // body zones + per-part zones
  palette: string | null,               // last applied preset palette id
  material: "standard-resin" | "premium-resin" | "full-color",
  sizeInches: 4 | 6 | 8
}
```

`handR2/handL2` slots exist only when `body.armCount === 4` (slot model computed by
`catalog/slots.ts`). Zone colors are keyed by stable zone ids so parts can be swapped
without breaking saved colors.

### 2.2 Postgres tables (Supabase; SQL in `supabase/migrations/`)

| Table | Columns (abridged) | Notes |
|---|---|---|
| `deities` | id, name_en, name_hi, **tier** (`A`\|`B`\|`C`), forms jsonb, default_config jsonb | Tier field exists NOW (M0 = Ganesh, tier A) |
| `parts` | id, deity_id (null = universal), category (`attire`\|`ornament`\|`ayudha`\|`base`\|`vahana`), tab, slot, name_en, name_hi, mesh_url, thumbnail_url, color_zones jsonb, constraint_tags text[], price_volume numeric, style_tags text[] | Matches kickoff schema exactly |
| `constraints` | id, deity_id (null = all), rule_type (`deny`\|`slot_allow`\|`limit`), part_tag, slot_pattern, max_count, reason_en, reason_hi | 5+ seed rules |
| `designs` | id (short code), owner uuid → auth.users, name, config jsonb, schema_version, is_public, created_at, updated_at | RLS: owner CRUD; public rows readable by anon |
| `orders` | id, user_id, design_config jsonb (frozen copy), material, size_inches, price_inr (server-computed), status (`stub_created`), razorpay_order_id (null — integration point), created_at | No payment in M0 |

The app bundles the same parts/constraints seed as static TS data (single source:
`lib/catalog/data/*` → seed SQL is generated from it), so builder reads are instant and
demo mode works; DB tables are authoritative for server-side validation when configured.

### 2.3 Seed constraint rules (5, Ganesh)

1. `slot_allow` — parts tagged `ankusha` only in **right**-hand slots (iconographic convention).
2. `slot_allow` — parts tagged `pasha` only in **left**-hand slots.
3. `slot_allow` — parts tagged `modak` only in **left**-hand slots (trunk reaches the sweet).
4. `limit` — parts tagged `unique-item` max 1 equipped (no duplicate ankusha/pasha).
5. `deny` — parts tagged `fierce` denied on deities tagged `saumya` (benign form) — Ganesh
   is saumya; blocks future fierce-form items by data alone.

### 2.4 Pricing model (M0)

```
price = round9( base(material) × sizeMultiplier(sizeInches)
        + volumeCharge(estimatedBoundingVolume(config), material)
        + Σ part.priceVolume × materialRate(material) )
```

- Bases: Standard Resin ₹1,499 · Premium Resin ₹2,499 · Full-Color ₹3,999
- Size multipliers: 4″ = 1.0 · 6″ = 1.55 · 8″ = 2.35 (sub-cubic: overheads don’t scale with volume)
- Bounding volume estimated from config (height/weight sliders widen the box; 4 arms and
  bases extend it) — pure function, unit-tested.
- `round9` rounds up to a ₹…9 ending. Live price recomputes on every store change.
